# Reflect

将一次人机协作中的纠错过程转化为可审核、可复用且不过度泛化的项目规则。默认只提出候选内容，不立即写入任何文件。

## 不可突破的边界

1. 仅响应用户对本 Skill 的显式调用。不要因为观察到用户纠错、验收失败或重复问题而自行启动。
2. 把“分析”和“写入”分成两个阶段。首次执行只能分析并展示完整候选补丁，必须停下来等待用户审核；不要在同一阶段修改记忆文件。
3. 默认唯一允许写入的目标是当前项目根目录下的 `AGENTS.md`。在 Git 仓库内以 `git rev-parse --show-toplevel` 的结果作为项目根目录；不在 Git 仓库内时以当前工作目录作为项目根目录。
4. 不要默认修改父目录、用户主目录、`~/.codex`、`~/.agents`、其他项目、全局 `AGENTS.md` 或任何其他记忆文件。“记住这个”“以后别再犯”“记录一下”不构成扩大范围的授权。
5. 用户明确指定默认范围之外的目标时，将其视为范围升级：先展示目标的绝对路径、影响范围和完整候选补丁，再取得针对该目标和该补丁的明确批准。目标不明确时不要写入。
6. 不要修改代码、配置、测试、文档或其他文件来顺带修复问题；如需这些改动，只能提出建议并等待用户另行授权。
7. 不要提交、推送或创建 PR，除非用户另行明确要求。

## 第一阶段：只读反省

### 1. 锁定证据范围

- 只使用当前可见对话、用户明确提供的材料，以及为核实现状而读取的当前项目文件。
- 找出原始目标、AI 的实际做法、用户的验收反馈、用户给出的纠正、纠正后的结果。
- 将内容标为“已确认事实”“合理推断”或“未知”。不要补造不可见的旧对话，也不要声称记得其他会话。
- 如果看不到具体纠错过程，说明缺少哪段证据，请用户提供或指出；不要凭空生成经验。

### 2. 还原纠错链路

按以下顺序分析：

1. AI 做错了什么，或遗漏了什么。
2. 错误为什么会发生：错误假设、遗漏检查、范围判断不当、验证不足，或对环境差异处理错误。
3. 用户的指导改变了哪个判断或动作。
4. 哪些证据说明纠正后的做法更可靠。
5. 哪些信息仍不足以支持长期规则。

不要把“用户这样说了”直接当作根因；需要提炼导致错误的决策缺口。

### 3. 判断是否值得记录

候选经验必须同时满足：

- **有证据**：能够对应本次对话中的具体纠错。
- **可复用**：未来在相似条件下能够指导明确动作。
- **有边界**：说明适用条件、不适用条件或例外。
- **可验证**：说明执行后如何检查结果。
- **适合放入 `AGENTS.md`**：属于长期协作约定，而不是更适合固化到代码、测试、类型、Lint、配置或业务文档的一次性事实。

以下内容默认不记录：临时偏好、尚未验证的猜测、只发生一次且不太可能重现的细节、现有规则已经完整覆盖的内容、真实凭证或个人敏感信息。若自动化约束比记忆规则更可靠，明确建议“不写入 `AGENTS.md`”，并说明更合适的承载方式，但不要擅自实施。

### 4. 防止矫枉过正

- 不要从一个案例推导“永远”“全部”“任何情况下”之类的绝对规则，除非证据确实支持。
- 一台电脑或一个项目存在多种合法情况时，提炼判断方法，不要记住单一结果。
- 优先使用“当条件 A 时先检查 X；若结果 B，则执行 Y；若结果 C，则执行 Z；最后用 V 验证”的结构。
- 明确区分项目特有事实、机器特有事实和可跨项目复用的方法。默认只保留对当前项目有价值的部分。
- 说明关键例外、兼容路径和失效条件。无法确定边界时，把它列为待审核问题，不要自行补全。
- 检查候选规则是否与目标 `AGENTS.md` 的现有规则重复或冲突。重复时优先建议不新增；冲突时展示冲突并请用户决定替换、合并还是放弃。

### 5. 生成可审核提案

使用以下结构输出；不要在该阶段调用文件编辑工具：

````markdown
### 反省结论

| 项目 | 内容 | 证据状态 |
|---|---|---|
| 原始目标 | ... | 已确认/推断/未知 |
| 出现的问题 | ... | ... |
| 用户的纠正 | ... | ... |
| 根因 | ... | ... |

### 抽象方法

[说明可复用的方法，以及为什么不会把一次案例过度泛化]

### 记录建议

- 建议：写入 / 不写入
- 目标文件：[绝对路径]
- 适用范围：[项目、条件]
- 不适用或例外：[边界]
- 验证方式：[以后如何判断规则被正确执行]

### 候选补丁

```diff
[展示将要新增、修改或删除的完整文本；不省略关键上下文]
```

### 等待审核

尚未修改任何文件。请批准、修改或拒绝以上候选补丁。
````

候选规则使用可执行措辞，至少包含“触发条件、应做动作、例外或分支、验证方法”。一次纠错涉及多个独立问题时，拆成多个候选规则，让用户可以分别批准或拒绝。

## 第二阶段：审核后写入

只有用户看过完整候选补丁后，明确表示批准该内容及目标文件，才执行写入。笼统的认可、继续讨论或要求进一步修改不算批准。

写入时：

1. 如果用户修改了候选内容，先输出修订后的完整补丁并再次等待批准，不要把修改意见当成写入授权。
2. 写入前重新确认目标绝对路径。默认目标必须恰好是 `<项目根目录>/AGENTS.md`；如果是符号链接且解析到项目外，停止并说明风险。
3. 重新读取目标文件，保留用户现有内容和无关改动。文件不存在时，只有候选补丁已经明确展示“新建该文件”且用户批准，才创建。
4. 只应用获批文本的最小补丁。不要顺带润色、重排或更新其他规则。
5. 写入后展示实际 diff，并核对它与获批补丁一致。若出现意外差异，停止并告知用户。
6. 报告实际修改的文件；没有修改时明确说明。

## 批准判定示例

- “批准以上候选补丁写入 `/path/to/project/AGENTS.md`”是明确批准。
- “第二条缩小到 macOS，再给我看”是修改意见：修订后继续等待，不写入。
- “挺好”“记住”“继续”不是针对具体补丁和目标的明确批准：继续等待。
- “写到全局记忆里”表达了范围意图，但目标仍不明确：先确认准确文件并展示影响，不能直接写入。
