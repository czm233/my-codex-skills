# Check

## 核心约束

1. 先判断任务处于“开发前”还是“开发后”；混合状态分别处理。
2. 以代码、配置、日志、报错、测试结果和可见对话为证据，区分已确认事实、合理推断和未知信息。不要把猜测写成根因。
3. 在开发前只执行只读检查。不要修改文件、运行会改写文件的格式化或生成命令、安装依赖、迁移数据、提交代码或改变外部系统状态。
4. 只有用户明确选择某个方案，或明确说“按推荐方案执行”，才开始修改或开发。仅调用 `$check` 不算实施授权。
5. 开发后只陈述能够从当前会话、最近一次可见的相关对话和实际变更中证实的工作。不要虚构不可见的历史，也不要把用户原有或无关改动归因于 AI。

## 判断阶段

- 如果尚未实施，或用户要求先诊断、分析原因、比较方案，进入“开发前检查”。
- 如果代码已经写完，或用户要求复盘、检查刚才做了什么、比较修改前后，进入“开发后复盘”。
- 如果一部分已经完成、一部分尚未实施，先复盘已完成部分，再对未完成部分执行开发前检查并等待选择。
- 如果无法判断阶段，先用只读方式检查可见对话、工作区状态和差异；仍无法判断时，简短说明缺少什么证据。

## 开发前检查

### 1. 定义问题

- 说明期望行为、实际行为、触发条件、影响范围和严重程度。
- 将用户描述转换成一个可验证的问题陈述，不要急于给解决方案。
- 缺少会实质影响方案选择的信息时，提出最少量的关键问题；能够通过只读检查确认时，优先自行检查。

### 2. 分析原因

- 检查相关代码路径、配置、数据流、错误信息和近期差异。
- 用清晰的因果链说明问题为什么发生，以及证据如何支持结论。
- 分别标注“已确认”“推断”“待确认”。没有足够证据时写成可能原因，并说明如何验证。

### 3. 提出并对比方案

- 提供至少两个真正可行且有实质差异的方案。不要为凑数量制造无意义方案；如果客观上只有一个合理方案，明确解释原因。
- 对比每个方案的解决思路、改动范围、优点、缺点、风险、实施成本、兼容性、维护性和回滚难度。
- 明确指出每个方案适用的前提，避免只列方案名称。

使用以下结构：

```markdown
### 问题
[期望、现状、影响]

### 原因
[因果链、证据、尚未确认的信息]

### 方案对比
| 方案 | 核心做法 | 优点 | 缺点与风险 | 成本 | 适用条件 |
|---|---|---|---|---|---|
| 方案一 | ... | ... | ... | ... | ... |
| 方案二 | ... | ... | ... | ... | ... |

### 建议
[推荐哪个方案、推荐理由，以及不选其他方案的关键原因]

### 等待选择
请选择方案；确认后再开始修改或开发。
```

### 4. 等待明确选择

- 给出有立场的推荐，但把最终选择留给用户。
- 在用户选择前停止实施，不要把“推荐方案”自动当成已获授权。
- 用户选择后，先简短复述选定方案、范围和关键风险，再开始实施并进行必要验证。

## 开发后复盘

### 1. 还原实际工作

- 优先使用当前会话中的工具操作和结果；必要时参考最近一次可见的相关对话。
- 使用 `git status`、`git diff`、文件内容和测试结果核对实际变化，但不要仅凭 Git 差异推断所有改动都由 AI 完成。
- 如果上一段相关对话不可见，明确说明无法读取，不要假装记得；改用现有差异和用户提供的材料描述可证实内容。

### 2. 对比修改前后

- 说明 AI 处理了什么问题、改了哪些关键位置、行为发生了什么变化。
- 将“修改前的问题或行为”与“修改后的实现或行为”逐项对应。
- 列出验证方式和结果；未运行的测试必须明确标注为未运行。
- 说明剩余风险、未完成事项或用户需要继续决定的内容。没有则明确写“无”。

使用以下结构：

```markdown
### 本次完成的工作
[按结果陈述 AI 实际完成的事项]

### 修改前后对比
| 对比项 | 修改前 | 修改后 | 影响 |
|---|---|---|---|
| ... | ... | ... | ... |

### 验证结果
[运行了什么、结果如何；哪些没有验证]

### 剩余事项
[风险、限制、待办；没有则写“无”]
```

如果没有发生实际修改，直接说明“本次没有修改代码或配置”，不要编造前后差异。
