# After Dev

在开发完成后生成可核验、便于快速 Review 的结果报告。以实际产物为准，不凭对话印象声称完成。

## 不可突破的边界

1. 在完成任何实际开发改动后、最终回复用户前执行本流程。
2. 按以下优先级取证：实际文件和版本差异 → 测试、构建及运行结果 → 当前会话工具记录 → 对话陈述。证据冲突时采用更高优先级，并说明冲突。
3. 只陈述能够证实的工作。不要把用户原有改动、其他任务改动或不可见历史归因于 AI。
4. 不要把“计划修改”“命令已运行”写成“行为已验证”。未运行、失败或无法确认的验证必须明确标记。
5. 如果实际实现偏离用户审批的方案、范围或验收标准，突出说明偏差及影响，不要隐藏在普通摘要里。
6. 只在业务流程、调用链、数据流、状态变化或用户操作路径确实改变时输出流程对比；没有流程变化时明确写“流程未变化”，不要制造无意义图示。

## 1. 还原实施基线

- 从当前可见对话中提取用户批准的方案、范围、不包含内容、风险和验收标准。
- 找不到审批记录时明确写“未找到可见审批基线”，不要假装记得上一段不可见对话。
- 检查工作区状态、差异、相关提交、实际文件和验证输出，确定真正发生的变化。
- 区分本次 AI 改动、任务开始前已有改动和无法确认归属的改动；只把有证据的部分写入工作成果。

## 2. 对照实际结果

- 按结果说明实际做了哪些工作，以及改变了哪些用户可感知行为。
- 将“修改前”与“修改后”逐项对应，避免只列文件名。
- 将“审批方案”与“实际实现”逐项核对，列出一致项、合理调整和未经审批的偏差。
- 根据验收标准逐项核验，使用“通过 / 未通过 / 未验证”三种状态，并附证据。
- 列出实际运行的测试、构建和检查；不要省略失败结果。

## 3. 对比流程变化

只有流程确实变化时，同时提供完整文字说明和 Mermaid 图：

- 解释旧流程从哪里开始、经过哪些关键节点、问题在哪里。
- 解释新流程改变了哪个节点、调用关系或判断条件，以及带来的影响。
- 用一个带“修改前”和“修改后”分区的 Mermaid 流程图表达差异。
- 说明没有改变的关键环节，避免让用户误以为全部重做。

如果流程未变化，在结果中写明“流程未变化，本次只调整了具体实现或表现”。

## 4. 输出 Review 报告

结论优先，使用紧凑结构：

```markdown
### Review 结论
[已完成 / 部分完成 / 未完成；是否符合审批方案]

### 本次完成的工作
- [实际成果和证据]

### 修改前后对比
| 对比项 | 修改前 | 修改后 | 影响 |
|---|---|---|---|
| ... | ... | ... | ... |

### 审批方案与实际实现
| 审批项 | 实际结果 | 状态 | 偏差说明 |
|---|---|---|---|
| ... | ... | 一致/调整/偏离 | ... |

### 流程变化
[有变化时提供文字和 Mermaid；无变化时明确说明]

### 验收与验证
| 验收项 | 证据 | 状态 |
|---|---|---|
| ... | ... | 通过/未通过/未验证 |

### 剩余事项
[风险、限制、失败项和待办；没有则写“无”]
```

如果没有发生实际修改，直接说明“没有检测到本次开发改动”，不要编造前后差异或完成情况。
