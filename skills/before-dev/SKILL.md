# Before Dev

把所有开发需求转换成便于用户理解和审批的决策材料。先分析，后审批；没有明确审批，不实施。

## 不可突破的边界

1. 在修改代码、配置、脚本、数据、设计或外部系统状态前先执行本流程。用户最初提出“帮我实现”“直接修改”只代表提出开发需求，不代表已经审批尚未展示的方案。
2. 审批前只执行只读检查。不要编辑或生成文件、安装依赖、运行会改写文件的命令、迁移数据、提交代码、启动会改变外部状态的操作。
3. 只把用户在看过方案后明确表达的“选择方案一”“按推荐方案执行”“批准，可以开始”等视为审批。追问、质疑、补充信息、否决或模糊认可都不算审批。
4. 以截图、代码、配置、日志、报错和可复现结果为证据，明确区分“已确认”“推断”“待确认”。不要把推测包装成根因。
5. 方案、范围、关键风险或验收标准发生实质变化时，停止实施，展示修订内容并重新等待审批。
6. 实施完成后、最终回复用户前，必须使用 `$after-dev` 复盘实际结果。

## 1. 理解需求

- 读取用户提供的文字、截图、报错和附件。截图存在红框时，优先把红框目标视为用户要处理的对象。
- 说明用户想达到什么结果、当前看到什么现象、影响谁、影响范围是什么。
- 能通过只读检查确认的信息先自行检查；只有缺失信息会实质改变方案时才提出关键问题。
- 判断属于故障修复、新功能、行为调整、重构、配置、迁移、基础设施或混合需求。

## 2. 分析现状

### 故障或异常

- 说明期望行为、实际行为、触发条件和复现路径。
- 沿调用链、数据流或状态变化定位原因，用“现象 → 直接原因 → 根本原因”的因果链解释。
- 没有足够证据时列出候选原因及验证办法，不要宣称已经找到根因。

### 新需求或主动改造

- 说明业务目标、当前流程、期望流程、范围、约束和不做什么。
- 不要为新需求虚构“错误原因”；改为解释现状为什么不能满足目标，以及需要改变哪些能力。
- 提前定义可验证的验收标准。

## 3. 形成方案

- 提供至少两个真正可行且有实质差异的方案。客观上只有一个合理方案时，明确说明原因，不要为了数量制造无意义选项。
- 对比核心做法、改动范围、优点、缺点与风险、成本、兼容性、维护性、回滚难度和适用条件。
- 给出明确推荐，解释为什么推荐，以及不推荐其他方案的关键原因。
- 说明预计修改位置、用户可感知变化、验证方式和验收标准。

## 4. 输出审批材料

结论优先，使用紧凑结构：

```markdown
### 需要你决定
[一句话说明本次需要审批的决定]

### 需求与现状
[目标、现象、范围；标明已确认、推断、待确认]

### 原因或能力缺口
[Bug 写因果链；新需求写现状与目标之间的差距]

### 方案对比
| 方案 | 核心做法 | 优点 | 缺点与风险 | 成本 | 适用条件 |
|---|---|---|---|---|---|
| 方案一 | ... | ... | ... | ... | ... |
| 方案二 | ... | ... | ... | ... | ... |

### 建议方案
[推荐项、理由、预计改动范围]

### 验收标准
- [可验证结果一]
- [可验证结果二]

### 等待审批
尚未修改任何内容。请选择方案或继续追问；明确批准后再实施。
```

## 5. 审批后的交接

- 收到明确审批后，先用几句话记录“选定方案、实施范围、不包含内容、关键风险、验收标准”，作为本次实施基线。
- 严格按照审批基线实施和验证；发现必须扩大范围时重新审批。
- 完成后把审批基线、实际差异和验证证据交给 `$after-dev`，不要直接用笼统的“已完成”结束任务。
