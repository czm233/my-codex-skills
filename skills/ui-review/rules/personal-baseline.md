# 个人工程基线

## UI-BASELINE-001 优先复用已有成熟控件
- 类型：个人基线，不计功能分
- 状态：已确认
- 适用条件：实现选择器、弹窗等基础交互控件；不限定框架版本，因为判断的是项目组件复用约定。
- 现象：项目已有适用组件，却另写重复实现，增加基础交互缺陷风险。
- 检查方法：检查项目组件规范、现有依赖和实际调用；对自定义控件确认是否存在现有组件无法满足的明确需求。
- 通过标准：优先采用项目已有组件或平台原生控件；必要的自定义实现有具体理由并验证行为。没有 shadcn 不算失败，安装了组件库也不算功能通过。
- 原因：用户希望减少重复实现基本控件造成的低级错误；不推断某个项目的具体根因。
- 解决办法：优先复用现有体系；缺少体系时结合项目约束选型，review 不自动引入新库。
- 来源与日期：用户明确工程偏好，2026-09-28。
- 验证记录：每个项目单独检查；尚无具体修复案例。

## UI-BASELINE-002 模糊判定必须可解释，说明入口要温和
- 类型：个人基线，不计功能分
- 状态：已确认
- 适用条件：界面展示 AI/规则产生的模糊判定（难度、占用、推荐度等）或专业术语的页面。
- 现象：只显示结论（如"有人做了""不适合上手"）不显示依据，用户需要反复向开发者询问；或把长篇判定逻辑直接铺在界面上干扰主任务。
- 检查方法：检查每个模糊判定/术语是否具备以下层次之一：行内 title 悬浮提示、点开的说明弹窗、（有实体的）展开行证据；说明弹窗入口是否为大标题右侧的问号按钮。
- 通过标准：每个页面标题行有"?"帮助弹窗（收录该页概念、每列含义、术语解释）；问号紧贴大标题右侧成组，不与右侧主操作按钮混排；模糊判定带行内 tooltip；涉及具体实体时展开行给出证据（链接）与判定规则。
- 原因：判定不可解释导致用户不信任、不敢依赖；长文说明铺界面又喧宾夺主。用户经多轮反馈确立的交互原则。
- 解决办法：统一"标题 + ? + 弹窗"帮助组件；判定证据随数据落库并透出到展开行；? 放标题左侧组、主操作独占行尾。
- 来源与日期：用户确立（多轮反馈），2026-10-02。
- 验证记录：单项目全部页面覆盖实测：弹窗可开、内容含判定规则与术语解释、布局位置经坐标测量。

## UI-BASELINE-003 列表每页条数默认 10，且记住用户自选值
- 类型：个人基线，不计功能分
- 状态：已确认
- 适用条件：所有带分页的列表页；不限定框架与平台。
- 现象：每页条数默认 25/50，与用户阅读习惯不符；用户自己改过每页条数后，刷新或重新进入又被重置回默认。
- 检查方法：检查列表初始每页条数是否为 10；修改每页条数后刷新页面、重新进入，确认保留用户值；清理本地存储后确认回到默认 10。
- 通过标准：默认每页 10 条；用户选择持久化（本地存储，按页面分键，各列表互不覆盖）；仅本地存储被清或值非法时回到默认。
- 原因：用户明确要求"分页默认一定要是 10 条，除非我自己去改"；此前默认 25 且不记忆用户选择。
- 解决办法：分页用统一组件时在组件层提供带持久化的每页条数 hook：默认 10，写入本地存储按页面分键，读取时校验值在合法选项集合（如 10/25/50）内，非法回默认。
- 来源与日期：用户明确偏好，2026-10-02。
- 验证记录：四个列表页默认 10；改 25 后刷新保留 25；清存储后回默认 10；选项下拉与翻页行为正常。

## UI-BASELINE-004 文本输入框聚焦时只保留一层清晰高亮边框
- 类型：个人基线
- 状态：已确认
- 适用条件：Web 应用中已有可见边框的文本输入框，聚焦样式同时可能来自组件和页面级规则。实测技术为 React 18、Tailwind CSS 4（关闭 preflight）与手写 CSS；不限框架版本，因为问题来自 CSS 层叠及多个装饰机制叠加。
- 现象：鼠标点击或键盘进入输入框后，原边框外又出现一圈分离的亮框，形成双边框；输入框本体、外轮廓和光圈同时变亮。
- 检查方法：分别用鼠标点击和 Tab 进入文本输入框，检查计算样式的 border、outline、outline-offset、box-shadow，以及组件库可能注入的 ring；对照未聚焦状态与截图。检查同一全局规则覆盖的按钮、链接、复选框，避免修复文本框时误删其他控件的焦点提示。
- 通过标准：普通主题下，文本输入框聚焦时只有一层可辨识的高亮边界，不叠加分离的第二圈；鼠标与键盘聚焦都能辨认。其他控件保留各自焦点提示。系统强制颜色模式等辅助功能场景需单独验证，不以去掉所有 outline 为通用目标。
- 严重程度与权重：个人基线，不计功能分；仅有双边框不推断关键操作不可用。
- 原因：已确认组件的 :focus 同时设置高亮 border 和 2px box-shadow，页面级 :focus-visible 又对所有 input 加上带 3px 偏移的 2px outline；文本框在鼠标点击后也可能匹配 :focus-visible，因此不是只有 Tab 操作才会叠加。
- 解决办法：实测项目让文本输入框的 :focus 只修改现有边框颜色，取消该控件自己的阴影和轮廓；页面级通用焦点选择器排除已有专用聚焦样式的文本输入框，继续保留按钮、链接及其他 input 的规则。这是该项目的已验证方案，其他组件体系可统一由 ring 或 outline 承担高亮，关键是单一职责且焦点可辨，不要求一律删除 outline。
- 来源与日期：用户明确偏好 + 源码核查 + 浏览器实测，2026-10-05。公开记录仅保留通用选择器和样式机制，不附项目、账号、页面内容或内部地址。
- 验证记录：普通主题的真实 Web 输入框鼠标聚焦后，计算样式为 1px 实线高亮边框、outline-style: none、box-shadow: none；截图确认单圈。Shift+Tab 移出再 Tab 返回后，输入框为活动元素且仍无额外轮廓和阴影。同步本机规则后另抽样一个使用相同样式的页面复测，鼠标与键盘结果一致，Tab 移到相邻按钮仍有实线焦点轮廓；链接、复选框、强制颜色模式与其他浏览器未专项验证。前端构建通过仅作补充证据，不替代焦点实测。

## UI-BASELINE-005 用途明确的快捷入口不重复铺陈功能说明
- 类型：个人基线
- 状态：已确认（用户偏好；案例最终视觉复验未完成）
- 适用条件：手机工具首页等以导航为主的入口网格，名称已足以区分用途；不限定框架版本，因为检查目标是信息是否重复。本案例使用 React 18 与基于 Base UI 的共享按钮。
- 现象：每张卡片同时显示图标、名称和一整句同义说明，抢占有限的手机空间；移除说明后仍保留原来的卡片高度，出现无用留白。
- 检查方法：逐项判断说明是否带来名称之外的必要决策信息；检查同类入口是否统一精简，源码和预览样例是否仍保留废弃说明；用支持的手机宽度核对卡片尺寸和按钮可访问名称。
- 通过标准：用途明确的入口以图标和名称为主，不重复解释名称；去掉说明后同步收紧留白，名称及触控目标仍清楚可用。确有前置条件、费用、风险或歧义的入口保留必要信息，不将本条用于隐藏决策依据。
- 严重程度与权重：个人基线，不计功能分。
- 原因：已确认入口数据中配置了统一 description 字段，视图无条件逐卡渲染，卡片最小高度也按含说明的结构设置。
- 解决办法：案例移除入口视图、数据和预览样例中的重复说明，降低卡片最小高度，保留原路径与可见名称。实现经源码及自动化核对；实际尺寸与留白仍待浏览器复验。含专业术语或模糊判定的帮助需求参照 UI-BASELINE-002，不为普通导航卡额外添加帮助按钮。
- 来源与日期：用户提供手机截图并明确要求精简，源码核查，2026-10-05；未保存原截图或内部页面内容。
- 验证记录：既有入口点击回调测试、客户端边界检查和构建通过；随后客户端 37 套 / 190 项测试通过。浏览器工具因策略校验不可用，修改后的视觉效果未自动复验；自动化通过不等于视觉已验收。

## UI-BASELINE-006 手机页头突出当前任务，避免重复堆叠标题
- 类型：个人基线
- 状态：已确认（用户偏好；不同页面的修复证据分别记录）
- 适用条件：已选择应用式导航栏的手机 Web 工具页、详情页或榜单页；不限定框架版本。内容阅读页、品牌介绍页不自动套用此布局。
- 现象：顶部同时堆叠分类小字、品牌大标题、页面标题和重复区块标题；对象名称被放成浅色副标题，通用页面类型反而占据视觉重点。
- 检查方法：清点首屏标题及其含义，确认对象名称和当前任务的主次；测量标题相对整条导航栏是否居中，而非仅在返回按钮右侧剩余空间中居中；检查长标题、返回按钮可访问名称和触控范围。
- 通过标准：同一层级只保留必要主标题，普通工具页可用单一用途名称，对象页可用“对象名称-页面用途”；本基线选择居中标题栏时须相对整栏居中。图标式返回按钮保留可访问名称和触控范围，长标题不挤压操作；页头与紧邻 Tab 不保留重复区块间距。
- 严重程度与权重：个人基线，不计功能分。
- 原因：已确认通用模板同时输出 title、subtitle、区块标题，页面沿用后没有按当前任务删减；带返回按钮的页头原先按纵向内容块排布。
- 解决办法：案例复用已有 Screen 组件，仅对指定页面组合为单行页头；有返回按钮的页面使用左右对称预留，使标题真正居中，并保留图标按钮的可访问名称。普通工具首页去掉品牌标题和重复区块标题，同时同步页面状态与预览样例中的标题。不要求所有项目采用固定高度、固定标题文案或相同组件名称。
- 来源与日期：用户多轮纠正手机页头并确认榜单标题栏方向，源码核查，2026-10-05。
- 验证记录：用户明确认可榜单居中页头及缩紧标题与 Tab 间距后的效果；这是用户验收证据，未冒充代理浏览器测量。工具首页改动的既有测试、边界检查及构建通过，但最终居中效果、长标题和键盘操作仍待浏览器复验。

## UI-BASELINE-007 信息行按可见锚点对齐，不以容器边界代替视觉对齐
- 类型：个人基线
- 状态：已确认（用户偏好；最终细节仍需按场景验证）
- 适用条件：用户已指定并列指标信息行，或指定图标与名称居中的导航卡片；不限定框架版本，判断的是可见内容的对齐关系。两种布局分别应用各自对齐标准，不要求所有文字居中。
- 现象：昵称、地区与底部时间看似在同一容器，却与指标标志错位；新增第一条左边线后边线向头像方向越界。入口卡片则仍使用左对齐与上下分散布局，未实现用户指定的整体居中。
- 检查方法：为每个信息组先选可见锚点，核对文字起点、标志左边缘、头像边界；改变手机宽度并加入长昵称、缺失值和真实零值。对居中入口卡分别核对图标中心、文字中心及整组内容中心，不能只检查 text-align。
- 通过标准：信息行中被约定对齐的昵称、地区、时间与首个指标标志共享同一可见起点，标志不越入头像空间；并列指标保持已约定的横向列关系，不擅自变成上下堆叠或带完整边框的表格。居中入口卡的图标与文字作为一组居中。数据缺失与真实零值仍可区分。
- 严重程度与权重：个人基线，不计功能分。
- 原因：源码确认，指标列内的内容居中与外层文字起点不是同一基准；增加首项左边线后，指标网格与文字块没有共用缩进。入口卡原样式为 align-items: flex-start 与 justify-content: space-between。
- 解决办法：案例让文字块、日期和指标网格共用左缩进，以最左侧标志为锚点，指标标签仍位于各自列内部；入口卡独立改为横纵居中。具体缩进公式、列数、头像尺寸和颜色只属于该案例，不提升为所有项目的固定实现，也不规定特定色板或奖牌画法。
- 来源与日期：用户提供手机截图并逐次指出可见对齐问题，源码核查，2026-10-05。
- 验证记录：用户认可榜单横向指标主体布局，并在首项边线对齐调整后确认可接受；榜单视图回归通过。后续首页居中改动只有源码、测试与构建证据，未获最终浏览器复验；多宽度及长内容几何检查仍未验证。

## UI-BASELINE-008 底部导航变更时同步可见项、布局和保留入口
- 类型：个人基线
- 状态：已确认（用户偏好；案例最终浏览器复验未完成）
- 适用条件：应用式界面按产品要求增减底部导航项；不限定框架版本。本条不规定所有产品必须有几项导航。
- 现象：删掉中间入口后，布局若仍按旧数量分列就会留下空位或不均衡；只删除可见项而未检查选中态与替代入口，也可能让既有功能难以进入。
- 检查方法：核对共享导航配置、图标导入、列数及索引依赖；检查剩余入口的名称、跳转和高亮；若用户只要求移除底栏入口，确认功能在约定的其他位置仍可达。
- 通过标准：底栏只显示当前批准的入口，等宽设计的各项平分可用宽度，无旧项占位；高亮与当前页面归属一致，不给已移除项目留下假选中状态。移除导航入口不擅自删除相关业务功能。
- 严重程度与权重：个人基线，不计功能分；若实测关键功能不可达，再单列功能故障。
- 原因：源码确认该案例导航来自共享配置，但 CSS 固定为三列；删除一项时必须同步两处。未把尚未实际发生的路由故障记成历史 bug。
- 解决办法：案例删除中间项及不再使用的图标，将网格改成两等宽列，保留原功能的首页入口；检查没有其他页面依赖旧项 key 或固定索引。两项是该项目本次要求，不推广为默认项数。
- 来源与日期：用户明确要求精简底栏，源码影响检查，2026-10-05。
- 验证记录：客户端 37 套 / 190 项测试、边界检查和构建通过；源码确认保留入口与路由存在，但现有测试不等同于真实底栏点击验收。浏览器工具不可用，两项宽度、选中态和真实跳转仍待复验。

## UI-BASELINE-009 同类控件变更须覆盖全部适用入口
- 类型：个人基线
- 状态：已确认（用户偏好；案例仅部分入口完成浏览器验证）
- 适用条件：用户要求统一某类控件的样式或通用交互，且产品存在多个同类入口；不限框架版本，因为检查的是变更覆盖范围。本例为服务端 HTML 模板、原生 JavaScript 与 CSS，自动化使用 jsdom 26.1.0。
- 现象：仅将薪资选择改为自定义下拉，地区、列表筛选、设置等入口仍保留旧实现，用户需要逐处指出遗漏。同类控件出现无业务理由的外观与操作差异。
- 检查方法：修改前检索公共模板、组件、页面及动态生成控件，列出适用入口；修改后逐类检查接入与遗留实现。实际打开弹窗内选择器、列表筛选与设置选择器，核对显示值、提交值、禁用态、联动选项、程序赋值和表单重置。单选、多选、文本自动补全分别核对，不因外观相近就混为同一语义。
- 通过标准：已约定统一的同类控件全部接入公共实现或公共规范，保留的例外有明确业务理由；无需用户逐页提醒。外观统一不能破坏数据提交、原有联动、禁用状态及键盘操作；只做源码覆盖或抽样测试时如实说明尚未实测入口。
- 严重程度与权重：个人基线，不计功能分。实际选择失败按 UI-COMMON-001 计分，浮层不可达按 UI-COMMON-003 计分，避免重复扣分。
- 原因：前一版只在局部页面加载薪资专用下拉脚本，没有将控件变更提升到公共模板及其他同类入口。UI-BASELINE-001 评价选型和复用，本条评价实施覆盖范围，不重复要求选用某个组件库。
