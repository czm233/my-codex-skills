# 检查流程

## 识别与选项

1. 确认当前项目根目录、项目约定、工作区状态和检查范围。默认检查当前项目可识别的主要界面与关键路径；大型项目明确抽样页面，不宣称遍历全部界面。没有业务项目时询问项目位置，不检查 skill 仓库本身来冒充 UI 验收。
2. 从依赖清单、锁文件、配置和实际源码识别平台、框架、组件库及版本；依赖声明不等于正在使用。多应用仓库分别识别。Swift 是语言，SwiftUI/UIKit 是 UI 框架，不能混为一个标签。
3. 读取 rules/index.md，再组合通用、平台、框架、组件库和个人基线规则。Tauri + React 应组合桌面、Web、React、Tauri 相关规则。缺少某类规则时说明知识覆盖缺口，不生成空文件或虚构历史经验。
4. 按每条规则的适用条件和版本筛选；待确认、废弃项不计分，保留跳过原因。按稳定 ID 去重，同一故障命中多条规则时关联一个问题，不制造多份缺陷。

## 验证

遵守项目端口、环境和账号约定；先检查运行进程的工作目录、端口归属与健康状态，再复用或启动。不得用另一工作区的旧服务充当当前版本。不得擅自停止未知进程或执行生产写操作。允许正常测试操作，使用已有测试数据；需要真实支付、删除真实数据或其他不可逆操作时停在边界并注明未验证。

先检查代码，再用可用的浏览器、客户端、模拟器或真机操作适用路径。功能规则所需运行证据不能被 build、截图或静态推断替代；截图只能支持它实际展示的事实。纯工程基线可用源码证据判定。

每个规则在每个范围内只有一个状态：
- 通过：所有已声明适用测试点执行成功，有证据。
- 失败：至少一个测试点已确认违反规则；列出位置、复现、预期/实际、影响与修复建议。
- 不适用：条件不成立，写原因。
- 未验证：条件成立或无法排除，但缺少环境/工具/账号/覆盖；写缺口。部分通过不能把整项标通过。

先生成明确的检查清单；测试中发现新的适用条件可补充并披露，不能通过缩小分母提高分数。证据记录代码位置、操作步骤、实际结果，必要时附脱敏截图或日志；没有执行就不要编造。发现规则外的明确故障也列入报告，单列、不临时混入评分；关键路径阻断仍影响验收结论。

## 评分与结论

功能规则权重固定：严重 5、一般 2、轻微 1。严重程度依据规则及当前业务影响，在验证前确定；变化时解释原因。个人基线单独报告合规情况，不混进功能得分。

- 功能得分 = 100 × 通过权重 /（通过权重 + 失败权重）。
- 验证覆盖率 = 100 ×（通过权重 + 失败权重）/（通过权重 + 失败权重 + 未验证权重）。
- 四舍五入到一位小数；不适用、待确认、废弃项排除。
- 没有已验证功能项：得分 N/A；没有适用功能项：覆盖率 N/A，不能写 100 分。
- 有确认的关键路径阻断：不通过。有其他失败项：存在问题，不判定全面通过。有未验证项或关键路径未测：验收未完成。全部适用项通过且关键路径完成：仅在声明范围内通过。

## 报告

默认在对话输出；长报告按项目交付约定保存 Markdown。不把项目报告写进公共 skill 仓库。

包含：
1. 结论、功能得分、覆盖率、阻断项数量与个人基线情况。
2. 项目版本/未提交状态、规则版本（源码 commit 可得则记录，否则记录本次加载规则文件的内容哈希）、平台/技术版本、页面/设备/视口和抽样边界。
3. 按严重程度排序的问题：规则 ID、位置、复现步骤、预期/实际、证据、影响、建议。疑似问题单独列为待验证，不当作确认失败。
4. 逐项表：规则 ID、检查对象、权重、状态、证据或未验证/不适用原因；展示计算分子分母。
5. 服务/客户端运行情况、可访问验收入口、未验证内容和用户需补充的条件。没有启动就明确说明。

规则版本或范围不同的分数不直接比较。报告只表示当前规则与抽样范围内的结果，不保证 UI 无其他缺陷。
