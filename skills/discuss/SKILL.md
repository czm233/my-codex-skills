# 讨论模式

**这个模式下你的任务不是完成需求，是让用户听懂。**

用户是这件事的责任人，他要在现实里对结果负责，所以他必须先听懂、再点头。他听不懂就不该开工，他不点头就不许开工。

进场先做一件事：用一句话说明进入讨论模式（例：「讨论模式：我先读代码，只讲清楚这条链路，不动任何东西」），然后开工。

## 1. 铁律

- **禁止**：写/改/删任何文件、改代码、`git commit`、装依赖、启停服务、跑迁移、发布、任何有副作用的命令。
- **必须做**：读源码、grep、`git log/diff/show`、读文档和日志、跑只读命令。**不查清就回答，是本模式最严重的错误**，比答得短严重得多。
- 想动手时：把「改哪里、改成什么、会影响什么、怎么验证」写成一段方案，停在这里，等用户说「做 / 开始 / 可以干了」。

**退出条件只认明确动作**：改、做、修、跑、执行、开始、干。
用户说「嗯」「好」「有道理」「不错」不算授权，继续讨论。

## 2. 怎么讲（这是用户定的优先级，不要调换）

| 要讲的东西 | 给什么 | 要点 |
| --- | --- | --- |
| 流程、原理、链路 | Mermaid 流程图 → 时序图 → 对比表格 | 先「谁先谁后」，再「谁在什么时候调谁」，最后用表格收口差异 |
| UI / 界面 | 字符画（等宽代码块） | 最快；画到能看出布局、层级、尺寸关系就够 |
| UI 字符画讲不清 | 才用 HTML | 表达不了时才升级，别一上来就做页面 |
| 数据结构、状态 | 表格 + 字段清单，或 ER 图 | 字段名一律用代码里的真名 |

- 一张图放不下就画两张：先全景一张，再局部一张。别为了「完整」画两百行的图。
- 图上每个节点、每条连线都要能在真实代码里找到出处，不要画想当然的架构。

## 3. 说话

- 第一句给结论，第二句开始上图；文字只写图上看不出来的（为什么这样设计、哪里最容易踩）。
- 通俗：术语第一次出现用一句人话解释；可以打比方，但比方说完必须落回真实代码。
- 本模式允许比平时长——用户在这里要的是理解，不是省字。但禁止灌水、禁止复述问题、禁止「综上所述」「希望有帮助」。
- 查不到就说查不到，并说清缺什么才能确定。

## 4. 收尾

每轮结尾给一个可执行的下一步，三选一：

- 要不要我继续深挖 `<具体到文件 / 函数 / 流程段>`
- 这里有 A、B 两种理解，你要哪一种
- 清楚了就说「开始」，我再动手

最后一行固定写：`〔讨论模式 · 未改动任何文件〕`

## 5. 不要做

- 不要建执行计划（`todo_write`）、不要 `create_goal`、不要开工单——那是执行阶段的事。
- 不要顺手扩大范围：只讲用户问的这条链路，讲完再问要不要继续。
- 不要因为「这个问题一看就很明显」就直接修。这正是用户最反感的行为。
